# Enums as type-safe objects with state and behavior

A task has a status: new, active, or done. Before enums, developers represented this with `int` constants (`0` for new, `1` for active, `2` for done) or with plain strings. Both are fragile: nothing stops a method expecting a status from receiving a month number, a country code, or a typo'd string, since the compiler sees only "an `int`" or "a `String`", with no idea which particular set of values is actually meaningful. Java's `enum` fixes this by making a fixed, named set of constants into its own genuine type, checked by the compiler exactly like any other type you have used.

This lesson treats enum constants for what they really are: full objects, each one a singleton instance of the enum class, capable of carrying its own fields, its own methods, and even its own per-constant behavior — not just a fancy label for a number.

What you will learn:

- How to declare an enum and use its constants safely, with compiler-checked type safety
- Built-in enum methods: `values()`, `valueOf()`, `name()`, `ordinal()`, and why `==` is correct for comparing them
- How to give an enum constructors, fields, and methods, including behavior that differs per constant
- Why persisting `ordinal()` as a durable identifier is fragile, and what to store instead
- `EnumSet` and `EnumMap`, the specialized, efficient containers built for enum values

## Declaring and using an enum

An `enum` declaration lists a fixed set of named constants. Each name becomes a compiler-checked constant of that new type:

```java
public class StatusBasics {
    enum Status {
        NEW, ACTIVE, DONE;
        boolean terminal() { return this == DONE; }
    }

    public static void main(String[] args) {
        Status status = Status.NEW;
        System.out.println(status);
        System.out.println("terminal? " + status.terminal());
        System.out.println("DONE terminal? " + Status.DONE.terminal());

        for (Status s : Status.values()) {
            System.out.println(s.name() + " ordinal=" + s.ordinal() + " terminal=" + s.terminal());
        }

        Status parsed = Status.valueOf("ACTIVE");
        System.out.println("parsed: " + parsed + ", same as constant? " + (parsed == Status.ACTIVE));

        Status a = Status.NEW;
        Status b = Status.NEW;
        System.out.println("a == b: " + (a == b) + ", a.equals(b): " + a.equals(b));

        switch (status) {
            case NEW -> System.out.println("just created");
            case ACTIVE -> System.out.println("in progress");
            case DONE -> System.out.println("finished");
        }
    }
}
```

Output:

```text
NEW
terminal? false
DONE terminal? true
NEW ordinal=0 terminal=false
ACTIVE ordinal=1 terminal=false
DONE ordinal=2 terminal=true
parsed: ACTIVE, same as constant? true
a == b: true, a.equals(b): true
just created
```

Every enum type comes with these built-in members, generated by the compiler, without you writing anything:

| Member | Returns |
|---|---|
| `values()` | an array of every constant, in the order they were declared |
| `name()` | the constant's declared name, exactly as written, as a `String` |
| `ordinal()` | the constant's position in the declaration order, starting at 0 |
| `valueOf("NAME")` | the constant with that exact name, or throws if none matches |
| `toString()` | by default, the same as `name()` (you can override it) |

Because each named constant is compiled into exactly one singleton instance of the enum class, **there is only ever one `Status.NEW` object in the entire program**, no matter how many times or where you write `Status.NEW`. That is exactly why comparing two enum values with `==` is not just allowed but genuinely correct and idiomatic — unlike with `String` in Lesson 2, there is no aliasing subtlety to worry about, because there is only ever one object per constant to begin with. `switch` also works naturally on enums, and since Java 14 the arrow form shown above requires no `break` statements and no fall-through risk.

`valueOf` is an **exact-match lookup**, not a forgiving parser for arbitrary user input:

```java
public class UnknownName {
    enum Status { NEW, ACTIVE, DONE }

    public static void main(String[] args) {
        System.out.println(Status.valueOf("NEW"));
        Status parsed = Status.valueOf("new");
        System.out.println(parsed);
    }
}
```

```text
NEW
Exception in thread "main" java.lang.IllegalArgumentException: No enum constant UnknownName.Status.new
	at java.base/java.lang.Enum.valueOf(Enum.java:293)
	at UnknownName$Status.valueOf(UnknownName.java:2)
	at UnknownName.main(UnknownName.java:6)
```

`"new"` in lowercase does not match the constant `NEW` — `valueOf` requires the name spelled exactly as declared, case-sensitive, with no trimming of whitespace and no fuzzy matching. If you need to accept messy external input (from a file, a web form, a database column written before your enum existed), write your own lookup that normalizes the input first and defines a clear behavior for values that do not match — you will build exactly this in a moment.

## Fields, constructors, and per-constant behavior

Because each constant is a full object, an enum can have private fields, a constructor that runs once per constant, and ordinary instance methods — and, when a constant needs to behave *differently* from its siblings, its own constant-specific method body.

```java
public class EnumWithFields {
    enum Planet {
        MERCURY(3.303e+23, 2.4397e6),
        VENUS(4.869e+24, 6.0518e6),
        EARTH(5.976e+24, 6.37814e6);

        private final double mass;
        private final double radius;

        Planet(double mass, double radius) {
            this.mass = mass;
            this.radius = radius;
        }

        double surfaceGravity() {
            final double G = 6.67300E-11;
            return G * mass / (radius * radius);
        }
    }

    interface Operation {
        int apply(int a, int b);
    }

    enum Calculator implements Operation {
        ADD {
            public int apply(int a, int b) { return a + b; }
        },
        MULTIPLY {
            public int apply(int a, int b) { return a * b; }
        }
    }

    public static void main(String[] args) {
        for (Planet p : Planet.values()) {
            System.out.printf("%-8s gravity=%.2f%n", p, p.surfaceGravity());
        }

        System.out.println("ADD(3,4) = " + Calculator.ADD.apply(3, 4));
        System.out.println("MULTIPLY(3,4) = " + Calculator.MULTIPLY.apply(3, 4));
    }
}
```

Output:

```text
MERCURY  gravity=3.70
VENUS    gravity=8.87
EARTH    gravity=9.80
ADD(3,4) = 7
MULTIPLY(3,4) = 12
```

`Planet`'s constructor runs once for each constant, at class-loading time, in declaration order, storing that planet's own mass and radius; `surfaceGravity()` is one shared method that produces a different result per constant because it reads each instance's own fields — no `if`/`else` chain on the constant's name required. `Calculator` goes further: `ADD` and `MULTIPLY` each supply their *own* body for `apply`, overriding the interface method individually, so calling `apply` on different constants runs genuinely different code, with no branching logic anywhere in sight. This pattern — an enum implementing an interface, with per-constant method bodies — is a clean, compiler-checked alternative to a `switch` statement scattered across the codebase every time new behavior is needed per status or per operation.

## Why persisting ordinal() is fragile

`ordinal()` looks like a convenient, compact identifier — it is just an `int`, after all. The danger is that it is **derived purely from declaration order**, and that order is exactly the kind of thing that changes over the life of a program.

```java
public class OrdinalFragility {
    enum StatusV1 { NEW, ACTIVE, DONE }
    enum StatusV2 { NEW, CANCELLED, ACTIVE, DONE }

    public static void main(String[] args) {
        int savedOrdinal = StatusV1.ACTIVE.ordinal();
        System.out.println("saved ordinal for ACTIVE in V1: " + savedOrdinal);

        StatusV2[] values = StatusV2.values();
        System.out.println("that same ordinal in V2 now means: " + values[savedOrdinal]);
        System.out.println("V2 ACTIVE's real ordinal is now: " + StatusV2.ACTIVE.ordinal());
    }
}
```

Output:

```text
saved ordinal for ACTIVE in V1: 1
that same ordinal in V2 now means: CANCELLED
V2 ACTIVE's real ordinal is now: 2
```

This program simulates exactly what happens to a real system: imagine `StatusV1` was today's enum, and a database row saved `ordinal() == 1` to mean "this task is ACTIVE". Months later, a developer inserts a new `CANCELLED` constant *before* `ACTIVE` (a perfectly reasonable, innocent-looking change) — and every previously saved `1` in the database now silently means something completely different, with no compiler error, no exception, and no warning of any kind. This is precisely the fragility the chapter's concept-check question is about: it is not that ordinals are random or that recompiling alone changes them (they do not, unless the source order actually changes) — it is that **inserting or reordering constants silently reassigns the meaning of every ordinal from that point onward**, and any data saved using the old ordinals becomes wrong without anyone being told.

The fix is to store a value you control explicitly, independent of declaration order, and to define what happens when a lookup finds no match:

```java
import java.util.HashMap;
import java.util.Map;

public class StableCode {
    enum Status {
        NEW("S1"), ACTIVE("S2"), DONE("S3");

        private final String code;
        Status(String code) { this.code = code; }
        String code() { return code; }

        private static final Map<String, Status> BY_CODE = new HashMap<>();
        static {
            for (Status s : values()) {
                BY_CODE.put(s.code, s);
            }
        }

        static Status fromCode(String code) {
            Status found = BY_CODE.get(code);
            if (found == null) {
                throw new IllegalArgumentException("unknown status code: " + code);
            }
            return found;
        }
    }

    public static void main(String[] args) {
        for (Status s : Status.values()) {
            System.out.println(s + " -> stored code " + s.code());
        }

        System.out.println("fromCode(\"S2\") = " + Status.fromCode("S2"));

        try {
            Status.fromCode("S9");
        } catch (IllegalArgumentException e) {
            System.out.println("rejected: " + e.getMessage());
        }
    }
}
```

Output:

```text
NEW -> stored code S1
ACTIVE -> stored code S2
DONE -> stored code S3
fromCode("S2") = ACTIVE
rejected: unknown status code: S9
```

`Status` now owns an explicit `code` field, assigned once per constant through the constructor exactly as `Planet`'s mass and radius were. Inserting a brand-new constant with a brand-new code between existing ones no longer disturbs any previously stored value, because nothing depends on declaration order anymore. `fromCode` also makes the "value not found" behavior an explicit, deliberate decision (throwing with a clear message) rather than an accidental crash or a silently wrong lookup — the same "decide the contract, then enforce it" discipline from Chapter 4's null-contracts lesson, applied here to an unknown-code contract instead.

## EnumSet and EnumMap

Because an enum's full set of constants is fixed and known at compile time, the JDK provides two specialized collections — covered fully as collections in Chapter 9 — that are dramatically more compact and faster than general-purpose alternatives specifically because they exploit that fact: `EnumSet` and `EnumMap`.

```java
import java.util.EnumMap;
import java.util.EnumSet;

public class EnumSetMapDemo {
    enum Status { NEW, ACTIVE, DONE, CANCELLED }

    public static void main(String[] args) {
        EnumSet<Status> openStates = EnumSet.of(Status.NEW, Status.ACTIVE);
        System.out.println("open states: " + openStates);
        System.out.println("contains ACTIVE: " + openStates.contains(Status.ACTIVE));
        System.out.println("contains DONE: " + openStates.contains(Status.DONE));

        EnumSet<Status> all = EnumSet.allOf(Status.class);
        EnumSet<Status> closed = EnumSet.complementOf(openStates);
        System.out.println("all: " + all);
        System.out.println("closed (complement): " + closed);

        EnumMap<Status, String> labels = new EnumMap<>(Status.class);
        labels.put(Status.NEW, "Just created");
        labels.put(Status.DONE, "Finished");
        labels.put(Status.ACTIVE, "In progress");
        System.out.println("labels in enum order: " + labels);
    }
}
```

Output:

```text
open states: [NEW, ACTIVE]
contains ACTIVE: true
contains DONE: false
all: [NEW, ACTIVE, DONE, CANCELLED]
closed (complement): [DONE, CANCELLED]
labels in enum order: {NEW=Just created, ACTIVE=In progress, DONE=Finished}
```

Internally, `EnumSet` represents membership as a compact bit vector indexed by each constant's ordinal (exactly the mechanism from Chapter 2's bitwise-flags lesson, but managed safely for you rather than hand-rolled with raw `int` flags), and `EnumMap` stores its entries in an array indexed the same way. Both iterate their elements in the enum's natural declaration order automatically, as the `labels` output shows — `DONE` was `put` last but still prints in the middle, matching declaration order rather than insertion order. Reach for these two types by default whenever a set or map's keys are all values of one enum type; they are simultaneously more memory-efficient and clearer in intent than a general-purpose `HashSet` or `HashMap` of enum values.

## Common mistakes

**1. Using `int` constants or raw strings for a fixed set of choices instead of an enum.** This throws away compiler checking entirely; any `int` or any `String` compiles, whether or not it represents a real, meaningful status.

**2. Persisting `ordinal()` as a durable identifier** (in a database, a file, a network message). Any later change to the constants' declared order silently corrupts previously stored meaning, with no warning.

**3. Using `valueOf` directly on untrusted or user-supplied text.** It throws `IllegalArgumentException` for anything not spelled exactly like a declared constant name; validate or normalize first, or write your own lookup with defined behavior for unknown input, as `StableCode.fromCode` does.

**4. Comparing enum constants with `equals` out of habit from `String`.** It works, but `==` is the idiomatic, and equally correct, choice for enums specifically because each constant is a genuine singleton.

**5. Cramming unrelated per-constant logic into one giant method with an `if`/`else` or `switch` on the constant's name**, when a per-constant method body (as `Calculator` demonstrates) would let the compiler enforce that every constant supplies its own implementation.

## Best practices

- Reach for an `enum` the moment you notice a fixed, named, closed set of choices, instead of `int` codes or free-form strings.
- Give an enum fields and a constructor whenever each constant naturally carries its own data, rather than looking that data up separately elsewhere.
- Never store or compare `ordinal()` as meaningful business data; store an explicit code or name instead, and write a lookup with a clearly defined answer for unrecognized input.
- Use `==` for enum comparisons; it is correct, fast, and clearly communicates that you are comparing a fixed, singleton constant.
- Reach for `EnumSet` and `EnumMap` by default whenever a collection's elements or keys are entirely values of one enum type.

## Summary

- An `enum` declares a fixed, named, compiler-checked set of singleton constants, each a full object that can carry its own fields, constructor-assigned state, and methods.
- `values()`, `name()`, `ordinal()`, and `valueOf()` are provided automatically; `valueOf` is an exact, case-sensitive match that throws for anything else.
- `==` is correct and idiomatic for comparing enum constants, because each one is the single shared instance for that name.
- An enum constant can override a method individually, giving clean, compiler-checked per-constant behavior without branching on the constant's identity.
- Persisting `ordinal()` is fragile because inserting or reordering constants silently reassigns what every previously stored ordinal means; store an explicit, independent code instead.
- `EnumSet` and `EnumMap` are compact, ordered, enum-specific alternatives to general-purpose sets and maps.
